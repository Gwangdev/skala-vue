# 서비스 개발·포트폴리오 자동화 하네스 v9.17

**설계 → 개발 → 검증** 파이프라인에, 개발 기록을 **증거 기반 포트폴리오·보고서·발표자료로 전환하는 단계**를 붙인 Claude Code 하네스다.
판단이 필요한 검토는 설계 단계에 모으고, 개발 중에는 명세와 코드를 기계로 대조한다.

**원본:** `https://github.com/Gwangdev/prompt-maker-harness` (private). 다른 환경에서 쓰는 법은 `USER_GUIDE.md` §2.1.

## 핵심 흐름

```text
설계 대화 + PROJECT_STATE + 코드/Git/테스트
→ /design   ← 판단이 필요한 검토는 전부 여기. 산출물은 SPEC.yaml
→ /build    ← 명세 항목 단위 반복. 검사는 첫 항목 1회 + 체크포인트 1회
→ /verify   ← 격리 컨텍스트 1회
→ /handoff document
→ project.yaml + PROJECTS.md 검토본
→ 사용자 승인
→ [ /handoff report · /handoff publish · /handoff ppt ]   ← 순서 무관, 필요한 것만
→ 프롬프트 실행 (Claude 또는 Codex, 그때 정함) → gate.py로 검증
```

## 산출물은 만들지 않고 넘긴다

`/handoff`는 문서·보고서·초안·PPT를 직접 만들지 않는다. 실행 가능한
**자립형 프롬프트**를 쓴다. `report`는 긴 컨텍스트 사본 대신 판단과 근거 위치만 담은
`report-brief.json`을 함께 만든다. 실행은 Claude가 해도 되고 Codex가 해도 된다 — 그때그때 다르게 쓰는
운영 방식을 하네스가 강제하지 않는다.

문체·시각 디자인은 스타일, 구성은 콘텐츠 계약과 선택된 프로필이 맡는다. 프롬프트는 이 파일들의
**경로**만 지정하고 실행 주체가 직접 읽는다. 어느 쪽이 실행하든 같은 파일을 읽으면 같은 결과가 나온다.

산출물이 돌아오면 `python3 tools/gate.py <경로>`로 검증한다. 보고서 브리프 축(R0~R4)과
문서 축(D1~D4)은 서로 다른 단계만 검사하며 실행 주체와 무관하게 같은 기준으로 판정한다.

## 보고서는 한 번 설계하고 한 번 쓴다

기본 사용법은 `/handoff report` 하나다. 하네스가 근거를 보고 `technical-project`,
`business-strategy`, `policy-research`, `brief` 중 하나를 고른다. 명시하려면
`/handoff report business-strategy`처럼 실행한다.

```text
증거 추출 + 판단 설계 1회 → report-brief.json
→ 경량 report-prompt.md → 작성 1회 → 통합 감사 1회
```

선택한 프로필 하나만 읽고, 프롬프트에 상태·로그·스타일 내용을 다시 복사하지 않는다.
`report-contract.md`는 주장–근거, Executive Summary, 차트 메시지, 작성 순서를 공통으로 정하고
프로필 파일은 보고서별 목차와 판단 기준만 정한다.

## 설계에 검증을 몰아넣는다

판단이 필요한 검토는 `/design` 한 곳에 있다. 개발 중에는 **기계 대조만** 돈다.

`SPEC.yaml`에 공개 표면을 적으면 `tools/gate.py`가 코드에서 뽑은 실제 엔드포인트와 집합 비교한다.

| 상황 | 판정 |
|---|---|
| 명세에 있는데 코드에 없다 | `S3` 누락 — BLOCK (개발 중에는 정보) |
| 코드에 있는데 명세에 없다 | `S4` 명세 대비 과잉 구현 — BLOCK |
| URI에 동사가 들어갔다 | `A1` — BLOCK |
| 컬렉션 전체를 지우는 `PUT`·`DELETE`를 노출했다 | `A4` — BLOCK (사유를 달면 통과) |
| 컬렉션 단수형·중첩 3단계·버전 접두사 혼재 | `A2`·`A3`·`A5` — WARN |

해석이 개입하지 않으므로 같은 입력에 항상 같은 답이 나오고, 컨텍스트를 거의 소비하지 않는다.
같은 컨텍스트가 자기 산출물을 다시 보는 자기검토와 달리 **새 정보를 만든다.**

**검사는 첫 항목에서 1회, 체크포인트에서 1회 돈다.** 검증된 관례를 되풀이하는 구간에서 반복 검사는 새 정보를 만들지 않는다. 첫 항목만 예외인 이유는 거기서 파일 배치·주석 형식·오류 처리 관례가 정해지고 이후 항목이 그것을 복제하기 때문이다.

## 커밋은 사용자가 한다

**하네스는 `git commit`·`git push`를 실행하지 않는다.** AI가 자동으로 커밋하면 단기간에 수십 개가 쌓여, 팀 리더가 히스토리로 진행 상황을 읽을 수 없게 된다. 커밋은 작업 로그가 아니라 **리뷰 단위**다.

체크포인트에서 하네스가 하는 일은 세 가지다.

```bash
python3 tools/gate.py . --commit   # 품질 판정 + 테스트 실행, 통과 시 기능별 분할까지 출력
```

그다음 **번호가 붙은 커밋 시나리오**를 기능 단위로 제시하고 멈춘다. 실행은 사용자가 한다.
개발은 파트로 묶어서 하더라도 커밋은 기능 단위로 쪼갠다 — 개발 리듬과 커밋 단위는 다른 문제다.

절차 전문은 `reference/commit-protocol.md`에 있고 **체크포인트에서만 로드**한다.

## 내부 자산은 제출물에 나가지 않는다

`PROJECT_STATE.md`·`PROJECT_LOG.md`와 작업용 라벨은 하네스 내부 자산이다. 게이트가 유출을 막는다.

| 코드 | 조건 | 등급 |
|---|---|---|
| `L1` | `[미검증]`·`[확인 필요]`가 제출물에 잔존 | BLOCK |
| `L2` | `[피드백N]` 등 내부 태그가 코드·문서에 잔존 | BLOCK |

코드 주석은 태그·번호 없이 **원인 → 과정 → 결론**으로 쓴다. 저장소를 처음 보는 사람이 읽는다고 가정한다.
하네스 자신의 파일(`reference/`·`tools/`·`.claude/`·상태 파일)은 검사에서 제외되므로 오탐이 나지 않는다.

## 스타일은 파일로 교체한다

| 산출물 | 문체·판단 | 시각 디자인 | 바꾸는 법 |
|---|---|---|---|
| 발표자료 `/handoff ppt` | `reference/ppt-style.md` | 동일 파일 | 파일 내용을 바꾸거나 `reference/examples/`의 예시로 덮어쓴다 |
| 보고서 `/handoff report` | `reference/report-style.md` | `reference/report.css`(색·조판 값) | 문체는 파일을 갈아끼우고(예: `reference/examples/report-style-academic.md`), 색·조판은 `/handoff report`의 인자(`black`·`orange`·`blue`·`vermilion` × `classic`·`modern`·`formal`)로 고른다. `formal`은 `examples/report-style-formal.md`를 함께 지정한다 |

커맨드에는 어떤 스타일도 하드코딩되어 있지 않다. 보고서는 문체와 시각 디자인이 서로 다른
파일이라 독립적으로 바꿀 수 있다 — 문체만 학술체로 바꾸면서 색은 그대로 둘 수 있다.

## 중요한 전제

- AI가 현재 세션 밖의 ChatGPT·Claude 대화에 자동 접근한다고 가정하지 않는다.
- 대화를 활용하려면 대화 내보내기나 승인된 요약 파일을 프로젝트에 넣는다.
- 자동화 기본 범위는 **로컬 초안 생성까지**다.
- Notion 업로드, 블로그 게시, Git push는 외부 전송이므로 별도 승인이 필요하다.

## 사용 순서

1. `PROJECT_STATE.md`의 규제·금지행위·데이터 등급 입력
2. `/design` — 범위·규제 확정, `SPEC.yaml` 작성, 논리 검토 → **승인**
3. `/build` — 명세 항목 단위 구현. 첫 항목에서 게이트 1회
   - 테스트 실패·예상과 다른 동작 → `/debug` (또는 `reference/debug-protocol.md` 로드). 고치면 `/build`로 복귀
4. 체크포인트 — `gate.py . --commit` → `/code-review` 1회 (외부 표면이 바뀌었으면 `/security-review`도 1회) → `--changeset` → 커밋 시나리오 → **사용자가 커밋**
5. `/verify` — 격리 컨텍스트 독립 검증
6. 필요 시 대화 요약 파일을 프로젝트에 추가
7. `/handoff document` 실행 후 `project.yaml`·`PROJECTS.md` 검토·승인
8. `/handoff report`·`publish`·`ppt` 중 필요한 것으로 프롬프트 생성
9. 생성된 프롬프트를 Claude나 Codex로 실행 → `gate.py`로 검증
10. 외부 게시는 검증을 통과한 초안을 최종 검토한 뒤 별도로 진행

`/insight`는 이 순서에 속하지 않는다. 파이프라인을 쓰지 않는 프로젝트에서도 단독으로 돌며,
인사이트 자산을 현재 코드에 대조(`read`)하고, 새로 나온 판단을 수집(`add`)하고, 하네스 승격 여부를 판정(`promote`)한다.

## 여러 프로젝트를 모을 때 (허브 — 지금은 구현하지 않음)

포트폴리오 갱신은 프로젝트가 끝날 때 발생하므로 **실시간 연동이 필요 없다.** 별도 도구를 만들지 않고, 필요해진 시점에 프로젝트들의 부모 폴더를 연결해 대화로 정리한다.

```
~/dev/
├── project-a/docs/portfolio/project.yaml
├── project-b/docs/portfolio/project.yaml
└── project-c/docs/portfolio/project.yaml
```

- 각 프로젝트가 **같은 스키마의 `project.yaml`을 남기므로** 수집은 나중에 기계적으로 가능하다. 표준화는 이미 끝나 있다.
- 경로 패턴만 일정하게 유지하면 `find . -name project.yaml`로 한 번에 걷힌다. 프로젝트마다 하네스를 같은 방식으로 배치하면 자동 충족된다.
- 그때 사람이 판단할 것 두 가지: **대표 프로젝트 선별**(전부 나열하면 인상이 흐려진다), **`status`가 `completed`가 아닌 항목의 표기 방식**. 둘 다 자동화 대상이 아니다.

## 알려진 한계

- **주석의 질은 강제할 수 없다.** 게이트가 이력 주석 부족을 경고하고 내부 태그 유출을 BLOCK하지만, 형식만 갖춘 껍데기 주석은 통과한다. 이 하네스에서 자동화되지 않는 유일한 지점이다.
- **게이트 임계값은 잠정이다.** 소수의 실제 산출물에서 역산한 값이라 오탐이 있다. 로직 버그는 `test_gate.py`로 미리 잡히지만 임계값(주석 40%·변동계수 0.45·커버리지 95%)은 본인 글·코드 분포에 달려 있다. 3~4회 사용 후 `tools/gate.py` 상단에서 조정한다.
- **게이트는 주석이 '왜'형인지는 세지만 그 '왜'가 맞는지는 모른다.** `원자적으로 처리된다` 같은 과잉 단언은 통과한다. 그 판단은 `independent-verifier`의 검증 항목 8번에 남겨져 있다.
- **`/verify`의 지적이 0건이면 코드에 역사가 남지 않는다.** 지적이 3건 미만이면 검증 기준이 무른 것이다.
- **게이트 축 7(S1·S2)은 정적 참조만 센다.** 리플렉션·DI·프레임워크 콜백으로 호출되는 메서드는 참조가 잡히지 않는다. 어노테이션 부착·접근자·표준 오버라이드는 제외했으나 그 밖의 오탐이 남을 수 있어 WARN으로만 낸다. 반대로 **문자열로 조립해 호출하는 경우는 검출하지 못한다.**
- `reference/report.css`의 판형·본문 폭·페이지 크기는 게이트(D8)가 산출된 PDF와 대조한다.
  단, 실제 글꼴 렌더링 품질(자소 깨짐·자간)은 실행 환경에 의존하므로 기계로 검증하지 못하고
  렌더 검수(전 쪽 PNG 확인)에 남는다.
- **명세 대조는 HTTP 엔드포인트만 본다.** 필드·응답 스키마·오류 코드는 대조하지 않는다. 오탐이 나면 게이트를 끄게 되므로 확실히 셀 수 있는 것만 센다.
- **추출 대상 프레임워크는 Spring·FastAPI·Flask다.** 그 밖의 프레임워크를 쓰면 코드에서 엔드포인트가 잡히지 않는다. 이 경우 게이트가 `S3` 한 줄로 원인을 알린다. `SPEC.yaml`을 비우면 이 축은 꺼진다.
- **`SPEC.yaml`이 없는 프로젝트는 이 축이 동작하지 않는다.** CLI·배치·라이브러리처럼 공개 표면이 HTTP가 아닌 경우가 그렇다.
- **`gate.py --commit`은 전체 테스트 스위트를 돌리므로 느리다.** 체크포인트에서만 쓴다. 인자 없이 돌리는 일반 게이트는 여전히 초 단위다.
- **테스트를 먼저 썼는지는 기계로 확인할 수 없다.** 최종 상태만 보면 순서가 남지 않는다. `/build`의 절차 규칙이고, 게이트는 그 대신 **항목별 테스트 누락(`T2`)** 을 센다 — 구현을 먼저 할 때 실제로 나는 실패 모양이다.
- **`T2`는 경로 리터럴을 문자열로 찾는다.** 테스트가 경로를 상수·변수로 조립하면 잡히지 않는다(미탐). 그래서 BLOCK이 아니라 WARN이다.
- **보안 축은 코드·설정만 본다(X1).** 문서(`.md`)는 대상이 아니다 — 검사 자체를 설명하는 예시 문자열이 정상적으로 들어가기 때문이다. 대신 문서에 실제 키를 적으면 잡히지 않는다.
- **보안 축이 예외로 죽으면 BLOCK이다.** 다른 축은 검사기 오류가 WARN 한 줄로 지나가지만, 축 X만 「돌지 않았다」를 차단으로 올린다. 검사되지 않은 것을 통과로 읽지 않기 위한 것이다.
- **`X2`·`X3`은 외부 도구가 없으면 WARN이다.** `semgrep`·`pip-audit`을 설치하지 않으면 통과가 아니라 **미검사**다. 통과로 읽지 않도록 문구를 그렇게 냈다.
- **JVM 의존성 취약점은 검사하지 않는다.** Gradle·Maven은 저장소마다 플러그인 설정이 달라 게이트가 대신 실행하지 않고, 검사되지 않은 사실만 `X3` WARN으로 알린다.
- **`--changeset`의 기능별 묶음은 엔드포인트를 선언한 파일만 자동 분류한다.** 설정·공통 모듈·테스트는 미분류로 남으므로 사람이 어느 커밋에 실을지 정한다.
- **체크포인트를 크게 잡으면 결함 국소화 비용이 커진다.** 결함이 한꺼번에 드러나 어느 기능이 원인인지 좁히기 어려워진다. 파트를 얼마나 크게 잡을지는 사용자가 정한다.
- **슬라이드 린터(`K1~K10`)는 형식만 본다.** `failure_mode`에 「주의가 필요함」을 넣어도 통과한다. 내용의 진위는 사람이 판정해야 한다. 규칙을 프롬프트에 그대로 넣었으므로 형식만 맞춘 껍데기가 나올 수 있다.
- 허브(여러 프로젝트 통합)는 구현하지 않았다.

- 하네스 문서 작성 규칙·복사 대상 목록: `MAINTENANCE.md`
